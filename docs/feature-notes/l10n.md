# Localisation (G13)

minivu's user-facing text lives in String Catalogs, one per target:
`Sources/MinivuCore/Localizable.xcstrings`,
`Sources/MinivuRender/Localizable.xcstrings` and
`Sources/Minivu/Localizable.xcstrings`. English is the source language.
The shipped languages are German (de), French (fr), Spanish (es), Italian
(it), Portuguese (Brazil) (pt-BR), Dutch (nl), Polish (pl), Japanese (ja),
Chinese (Simplified) (zh-Hans) and Korean (ko).

> **Every translation is a machine translation and needs review by a native
> speaker.** Each one is entered with the catalog state `needs_review`. A
> reviewer who checks a string sets it to `translated` (Xcode's catalog
> editor does this, or edit the JSON). Nothing marks a string reviewed
> automatically.

Done so far: the infrastructure, the main menu (with everything it takes its
titles from), and the colour label names in MinivuCore, which are translated
into all ten languages. Everything else is still English. The Minivu catalog
already lists every SwiftUI literal the compiler found, with no translations.

## What the spike proved (Swift 6.4.2, Xcode 27.2)

- **`swift build` compiles the catalogs.** It uses Swift Build, the default
  engine (`.build/debug` points at `.build/out/Products/Debug`). With
  `defaultLocalization: "en"` in Package.swift, it finds each target's
  `Localizable.xcstrings` without a `resources:` entry and compiles it into
  the target's resource bundle as
  `<lang>.lproj/Localizable.strings` and `.stringsdict` (plurals). No
  script and no `xcstringstool compile` step are needed. The deprecated
  `--build-system native` ignores catalogs: the file is "unhandled" and
  `Bundle.module` doesn't exist.
- **The compiler writes the extraction data.** It writes one `.stringsdata`
  per source file beside the objects. That file lists every literal that
  became a `LocalizedStringResource` or `String.LocalizationValue`, with
  interpolations turned into format specifiers (`%lld`, `%@`). Then
  `xcrun xcstringstool sync <catalog> --stringsdata …` merges them into the
  catalog. `sync` matches a catalog to its table by file name, so the
  catalog must be named `Localizable.xcstrings`. It added nothing to a
  catalog with any other name.
- **Comments are extracted only from `String(localized:…comment:)` and the
  `LocalizedStringResource` initialisers.** A custom function's `comment:`
  argument is not extracted, but its `LocalizationValue` or
  `LocalizedStringResource` literal is. That is why the helper takes a
  `LocalizedStringResource` (below).
- **`String(localized:bundle:locale:)` does not choose the language.** Its
  `locale` sets the formatting and the plural rule only. To get a given
  language, use a `LocalizedStringResource` with that `locale`.
- **Bundles follow the main bundle's language.** A resource bundle shows the
  language the main bundle chose, and the main bundle chooses only among
  its own localizations. A bare executable, or an .app without
  `CFBundleLocalizations`, stays in English even under
  `-AppleLanguages (de)`. With the key set, the bundles switch.
- **Bundle.module works in the .app.** Swift Build's generated
  `Bundle.module` is `nonisolated` and looks in `Bundle.main.resourceURL`
  first, so it finds `Contents/Resources/minivu_<Target>.bundle`.
  `swift test` finds the bundles too.

## How it fits together

- `Package.swift`: `defaultLocalization: "en"`.
- Each target has `localized(_:locale:)`, an internal function in
  `Localized.swift`. It looks the string up in the target's own bundle:
  `Bundle.module` in MinivuCore, `Bundle.minivuRender` in MinivuRender and
  `Bundle.minivuHelp` (the `minivu_Minivu.bundle`) in Minivu.
  All three call `Bundle.localizedText` in MinivuCore. Without a locale,
  the text is in the bundle's first preferred localization, with that
  language's plural rule and the user's region. With a locale (tests), it
  is in that locale's language.
- `scripts/make_app.sh` copies all three bundles into `Contents/Resources`.
  It also copies the Minivu bundle's `.lproj` folders into the main bundle,
  because SwiftUI's `Text("…")`, `Button("…")` and the like look in
  `Bundle.main`. The Info.plist gets `CFBundleDevelopmentRegion` `en` and
  `CFBundleLocalizations` with all 11 languages. That makes the main bundle
  (so AppKit's Services menu, Window menu additions and standard panels)
  and every resource bundle follow the user's language. No empty `.lproj`
  folders are needed.
- Help pages: English pages stay in `Sources/Minivu/Help/HelpPages/`. A
  translation goes in a folder named for its language, spelled as the
  catalog spells it: `HelpPages/de/Browser.md`, `HelpPages/pt-BR/…`,
  `HelpPages/zh-Hans/…`. `HelpLibrary.markdown` takes the page from the
  first of the bundle's preferred localizations that has it, and otherwise
  the English page. Translate a whole page or none of it, keep its
  `help:` links and headings' structure, and translate the `# Title` to
  match `HelpPage.title` in that language.

## Conventions (follow these exactly)

**Writing a string.** Inside any target, write

```swift
localized("Open in Viewer")
localized(.init("Tag", comment: "Verb: menu command that tags the image"))
localized(.init("\(count) images", comment: "Status bar"))
```

- The argument is a `LocalizedStringResource`, so the literal is extracted
  and its interpolations become specifiers. Never build the text from
  pieces (`"Rate " + n + " Stars"`), and never pass a `String` variable as
  the key.
- Ignore the bundle a `LocalizedStringResource` names. The helper always
  looks in the calling target's own bundle.
- In tests, `localized("…", locale: Locale(identifier: "de"))` gives the
  German text. Tests otherwise run in English, so existing tests that
  compare English titles keep working.
- The main menu's private `NSMenu.add(_:…)` takes the
  `LocalizedStringResource` directly (`menu.add("Crop…", .cropImage, "k")`).
  `add(title:…)` takes text that is already localized, and
  `add(submenu:)` titles the item as the submenu.
- SwiftUI: `Text("Name")`, `Button("Cancel")`, `Toggle("…")`, `Picker("…")`
  and `.help("…")` literals are already extracted, and they resolve from
  `Bundle.main` in the .app (see make_app.sh above). Under `swift run` and
  in tests they show English. For a `String` that is already localized, use
  `Text(verbatim:)` or the `String` initialisers. Don't localise twice.
- AppKit text set in code (`title =`, `stringValue =`, `messageText =`,
  `NSMenuItem(title:)`, `toolTip`, `setAccessibilityLabel`) goes through
  `localized(…)`.

**Comments.** Add a `comment:` whenever a translator could misread the
English. Typical cases are a word that is both verb and noun ("Open",
"Tag", "Rename", "Filter", "Copy"), a word with several meanings ("Frame…"
the effect versus a video frame, "Zoom" the window versus the image), an
Apple feature name ("Live Text"), or a placeholder whose content isn't
obvious ("%@ or More", where %@ is ★ characters). Say what it is, then
what it does: `"Verb: crop the image"`, `"Noun: submenu of star
ratings"`. When the same key appears in several places, give it the same
comment everywhere or none at all. Otherwise sync joins the comments with
a newline.

**Keys.** A literal is its own key, and one key has one translation. A
comment only helps a translator choose; it can't give German "Tag" both as
the verb ("Taggen") and the noun ("Schlagwort"). When the same English means
two things in the UI (Open, Tag, Rename, Filter, Copy, Label, Zoom, Frame…),
give the less common meaning its own key and keep the English as the default
value:

```swift
localized(.init("menu.tag.verb", defaultValue: "Tag", comment: "Verb: tags the selected images"))
localized(.init("status.images", defaultValue: "\(count) images", comment: "Status bar"))
```

Keys are lower-case dotted names, `area.thing[.meaning]`, with no format
specifiers. Sync adds the key with the English as its `en` value, and
`localized` looks it up by key, falling back to the default value while the
catalog doesn't have it. Use a key only for such a clash or when the English
is too short to translate on its own; everything else stays a plain literal,
so most of the catalog stays readable as English. Never rename a key that
has translations without moving them.

**Plurals.** Interpolate the number:
`localized(.init("\(count) images", comment: …))`. Then give English plural
forms in the catalog for that key: `one` "%lld image" and `other` "%lld
images" (`MenuStateTitles.rating` and "Rate %lld Stars" are the example).
Never choose between singular and plural in code, and never append an
"s". Each translation then needs that language's plural categories: only
`other` for ja, zh-Hans and ko; `one`, `few`, `many` and `other` for pl;
`one`, `many` and `other` for fr, es, it and pt-BR. No other categories, except an optional
`zero`. A `zero` form may leave out the number, and so may a `one` form in
de, nl, es, it and pl, where `one` means exactly 1 ("Datei"). In fr and
pt-BR `one` covers 0 as well, so it keeps the number ("%lld fichier"). Every
other form must keep English's specifiers.
`translationsKeepSpecifiersAndPlurals` checks all of this.

**Do not localise:**

- log and `os.Logger` messages, `print`, `assert` and `fatalError` text;
- file-format and codec names and extensions (JPEG, HEIC, AVIF, PNG, "TIFF",
  UTType identifiers);
- UserDefaults keys, notification names, accessibility *identifiers*
  (`setAccessibilityIdentifier`, `NSUserInterfaceItemIdentifier`) and menu
  identifiers;
- SQL, catalog column names, JSON keys, saved-search criteria and anything
  written to disk or to the pasteboard as data;
- EXIF, IPTC and XMP field keys, and values written into files (`xmp:Label`
  takes `ColorLabel.name`; the menus show `localizedName`);
- Finder tag names (`ColorLabel.name` is the tag minivu writes);
- test fixtures, debug-only environment variables, Shortcuts parameter
  identifiers;
- the app's name, "minivu".

Keep such text out of the catalog: `Text(verbatim: "JPEG")`, a `String`
variable, or `String(…)` rather than a literal in `Text`, `Button`,
`Picker`, `.help` or `localized`. A literal that is already in the catalog
and must stay as it is (format names in a picker, "", "%", "px", "×",
"180°", "⌘E", a layout such as "%@  %@") gets `"shouldTranslate" : false` on
its entry. Sync keeps that flag, and `translationsAreComplete` skips the
entry, so no language translates it. Units and punctuation that do vary
("%lld%%", which French writes "50 %", "%@: %@", "— %@") stay translatable.

## Running the sync

```sh
scripts/l10n-sync.sh            # through the throttle on a shared Mac:
throttle.sh build scripts/l10n-sync.sh
```

The script builds (debug, Swift Build), reads the `.stringsdata` of the
files each target compiled (generated sources left out), and runs
`xcstringstool sync` on each catalog. New keys arrive untranslated, with
their comments. Existing translations and their states are kept. Keys no
source uses any more are marked `"extractionState" : "stale"`. Delete them
once their translations aren't wanted. Run the script after
changing strings and commit the catalogs with the code, except during a
parallel wave (see "Working in parallel"). Sync rewrites a
catalog only when its content changes, in its own format: keys, fields and
languages sorted, `" : "`, two-space indents, no final newline. English plural
forms and translations go in through
`scripts/l10n-merge.py` (below), which writes the same format, so a later
sync changes nothing. For any other edit (deleting stale keys, setting
`shouldTranslate`), change the JSON in Python, then run
`scripts/l10n-merge.py` with no arguments: it rewrites every catalog in
sync's format.

## Translating

`scripts/l10n-merge.py --todo de > /tmp/de-todo.json` lists every live key
German lacks, per target, with its English (each plural form), its comment
and, for a plural key, the categories German needs. Write the translations
as a file named for the language,

```json
{"Minivu": {"Open in Viewer": "In Viewer öffnen",
            "%lld images": {"one": "%lld Bild", "other": "%lld Bilder"}}}
```

and run `scripts/l10n-merge.py de.json`. It enters each one with the state
`needs_review` and refuses the whole file if a key isn't in the catalog. A
file named `en….json` sets English plural forms (state `translated`) the
same way. Translate a language for a whole catalog at once.
`LocalizationTests.translationsAreComplete` skips a language that has no
entries in a catalog, but fails a language that has only some. A language
that is half done in a catalog would mix English into its menus. Worse,
under a language's own plural rule an untranslated plural key shows its
English `other` form ("1 files" in Japanese).
`translationsKeepSpecifiersAndPlurals` checks every translation's
specifiers and plural forms against English.

## Working in parallel

Each target has one catalog, and every key's translations sit side by side
in it, so two branches that touch a catalog conflict on almost every key.
Only one place ever writes a catalog: the integration branch
(feature/l10n), one step at a time. Agents commit sources and translation
files, never catalogs.

1. **Converting code (split by area or file).** Wrap the strings in
   `localized(…)`, give comments and keys as above, and commit only
   Swift. Run `scripts/l10n-sync.sh` locally if you like, to see your keys,
   then `git checkout -- 'Sources/*/Localizable.xcstrings'` before
   committing. English plural forms for your new plural keys go in
   `l10n/en.<area>.json` (a file name no other agent uses), committed.
2. **Integrating the conversions.** Merge the branches one at a time (only
   Swift and `l10n/` files, so conflicts are real code conflicts), then run
   `scripts/l10n-sync.sh` and `scripts/l10n-merge.py l10n/en.*.json`,
   delete those files and commit the catalogs: "Sync the catalogs".
   MinivuCore's colour labels and anything else already translated stay
   complete only if no new key lands in their catalog; otherwise
   `translationsAreComplete` names the gaps, and step 3 closes them before
   the wave is merged.
3. **Translating (one agent per language).** Start from the synced
   integration branch. Run `--todo <lang>` and commit only
   `l10n/<lang>.json` (pt-BR.json, zh-Hans.json). Check it with
   `scripts/l10n-merge.py l10n/<lang>.json` and the LocalizationTests, then
   `git checkout` the catalogs again. Each agent owns a different file, so
   these branches never conflict.
4. **Folding in.** On the integration branch, merge the translation
   branches, run `scripts/l10n-merge.py l10n/*.json`, delete `l10n/`, run
   the LocalizationTests and commit the catalogs once. Help-page
   translations live in per-language folders and merge as they are.

After the wave, a branch that changes strings rebases onto main, runs
sync, and commits the catalogs with the code. **A catalog conflict is never
resolved by hand:** take the other side's catalog
(`git checkout <main or the branch you merge> -- Sources/<T>/Localizable.xcstrings`),
run `scripts/l10n-sync.sh`, re-run `l10n-merge.py` with any translation
files not yet folded in, and commit the result.
